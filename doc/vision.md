# SiteSensory 開發理念

## 產品定位

SiteSensory 是一個以網站視覺為核心的靈感資料庫。它協助 UI/UX 設計師、前端工程師、產品經理與行銷人員，從大量網站中找到值得參考的案例，並理解這些案例的產業、視覺風格、色彩、版面與互動特徵。

平台收錄內容時，由受保護的內部 API（應用程式介面）接收網址，再交給背景工作自動找出可公開存取的首頁與內頁、擷取畫面及頁面結構，並由人工規則與 Vision AI（視覺人工智慧）整理成可搜尋、可比較的資料。前台不提供輸入網址或抓取網頁的功能。產品價值不在於蒐集最多網站，而在於把原本分散、難以比較的設計案例整理成可信且能持續更新的資料。

## 要解決的問題

現有網站靈感平台多半依靠人工投稿、編輯分類或單張截圖。使用者雖然能瀏覽漂亮的畫面，卻很難用產業、版面結構、色彩、風格或動態程度找到真正適合手上工作的案例。截圖也容易在原網站改版後過時，讓讀者無法判斷目前看到的是現況還是歷史設計。

SiteSensory 要補上三個缺口：

- 自動把網站及其內頁轉成結構化資料，降低收集與整理成本。
- 以一致的方法描述網站與頁面用途，使不同案例能被搜尋與比較。
- 保存頁面改版前後的版本關係，避免資料重複，也保留設計變化的價值。

## 核心使用情境

使用者只能搜尋與整理平台已經收錄的資料，不能提交網址或要求系統抓取新網站。使用者可以從產業、網站語言、頁面類型、頁面結構、視覺風格、色彩、美感評分與動畫等級探索網站及內頁。例如，使用者可以只搜尋不同網站的「關於我們」頁面，或集中查看「最新消息」列表與內容頁的設計。每個搜尋結果與頁面詳情都要顯示相對應的頁面圖片，並提供可直接前往原始頁面的連結。進入頁面詳情後，使用者可以查看完整頁面截圖、導覽選單與內容清單等重點區域，了解平台提取出的設計特徵，並繼續瀏覽系統推薦的相似設計。

產品公開部署後，會員可以透過第三方身分驗證服務註冊或登入，把喜歡的頁面加入個人收藏，並用類似 Pinterest 的自訂標籤建立自己的標籤版圖。同一個收藏可以同時套用多個標籤，例如把某個頁面標成「關於我們參考」、「深色介面」與「品牌故事」。會員也可以在收藏頁面的圖片下方寫下收藏原因。會員可以依標籤查看收藏，其他會員不會看到或受到這些私人標籤與收藏原因影響。初期本機版本先使用單一管理者或本機帳號驗證這套流程，不因尚未公開而放棄會員資料的權限邊界。

## 開發原則

### 平台收錄與會員收藏是兩條不同路徑

平台收錄是後台資料工作。只有經過驗證的內部系統可以透過收錄 API 傳入網址，觸發網址正規化、重複檢查、內頁探索、截圖、AI 分析、品質檢查與入庫。前台使用者不能呼叫這條流程，也看不到輸入網址的介面。

會員收藏是前台個人整理功能。會員只能從已公開的頁面中搜尋、框選視角、收藏、加上私人標籤與收藏原因，不能因為收藏操作而觸發新的網站擷取。文件中的「收錄」固定指平台建立公共資料，「收藏」固定指會員保存既有頁面，兩者不得共用權限或工作狀態。

### 網域識別網站，網址識別頁面，畫面代表版本

資料要明確分成網站、頁面與頁面版本。網站代表同一個品牌或網域；頁面代表首頁、關於我們、最新消息或其他有獨立用途的內頁；頁面版本則保存同一頁面在不同時間的設計。

平台不應因為網址寫法不同，就把同一個頁面收錄多次。網址進入系統後，必須先移除追蹤參數、統一協定與主機名稱、處理結尾斜線，並盡可能採用頁面的 canonical URL（標準網址）作為比對依據。重新導向後的最終網址也要納入判斷。

網址相同不代表內容永遠相同。系統再次擷取已收錄頁面時，應把新畫面與最近一次成功擷取的畫面比較。如果差異很小，只更新檢測時間與必要的分析資料，不新增公開項目；如果差異足以表示頁面已明顯改版，則在原頁面下建立新的版本，重新分析並保留先前版本。

圖片差異的門檻不能只依賴像素變動。輪播圖、廣告、日期、Cookie 提示或個人化內容都可能造成畫面不同，但不代表設計已更新。判斷應結合版面結構、主要區塊位置、色彩分布與感知圖片相似度，並保留人工覆核與修正結果的能力。實際門檻要用真實擷取資料校正，不在理念階段寫死。

### 每個頁面都能看見畫面並回到原站

每個公開頁面都必須有可辨識的預覽圖片、完整頁面圖片與原始頁面連結。圖片、最終網址、擷取時間與頁面版本要成套保存，確保使用者看到的圖片確實來自該次擷取，而不是其他頁面或不同版本。

原始頁面連結要能從搜尋結果及頁面詳情直接開啟，並清楚標示這會前往外部網站。原網站日後改版時，平台保存的舊圖片仍可作為歷史版本，但必須標示擷取時間；原始頁面若已失效，圖片可以保留，連結則要顯示目前無法存取，不能讓使用者以為仍可前往。

### 框選視角同時驅動收藏與相似搜尋

頁面詳情要提供與視覺搜尋工具相同的直接操作感。完整頁面圖片顯示在上方，使用者可以在圖片上拖曳建立選取框，移動選取框，或拖曳邊線與控制點調整大小。選取框內維持清楚，框外以遮罩降低明度，讓目前搜尋的區域一眼可辨。使用者也能清除選取，回到以整個頁面搜尋。

選取區域改變後，下方的相似設計清單要依該區域更新，而不是繼續使用整張頁面的相似度。搜尋結果顯示候選頁面中相符的區域；點開結果後仍能查看完整頁面、原始連結與其他分析資料。互動方式應保持直接與連續，但介面樣式沿用 SiteSensory 自己的設計，不複製其他產品的品牌圖示或裝飾。

使用者收藏時可以保存目前框選的視角。收藏清單以這個區域作為主要預覽，點開後仍能回到完整頁面。框選不是建立新的頁面或複製完整圖片，而是記錄所屬頁面版本、原始圖片及選取範圍；為了加快顯示，可以另外產生可重建的裁切預覽圖。

框選位置以相對於原始圖片寬高的比例保存，不使用顯示畫面上的固定像素。這樣即使收藏卡片或裝置尺寸改變，仍能顯示相同區域。同一頁面可以收藏多個不同視角，每筆收藏各自保存框選範圍、私人標籤與收藏原因。沒有框選時，整張頁面圖片就是該筆收藏的視角。

### AI 提供一致的判讀，不宣稱絕對客觀

美感包含主觀判斷。AI 可以按照固定準則評估視覺層級、色彩、排版、風格完成度與互動細節，但分數不應被描述為設計品質的絕對答案。

每次分析必須保留評分準則、模型版本與分析時間，讓同一批資料可以重跑和比較。當評分方式改變時，系統應能區分舊結果與新結果，避免看似精確的分數其實來自不同標準。產品介面也應展示各項分數與判斷依據，而不是只給一個總分。

### 相似設計要兼顧用途與視覺

系統應根據頁面圖片及結構化分析結果，自動找出相似設計。相似度要綜合頁面類型、版面結構、色彩分布、字體表現、視覺風格與動畫等級，不能只因為兩張圖片顏色接近就判定為相似。使用者框選區域後，以框選內容作為主要視覺條件，頁面類型與整頁分析結果則作為搜尋限制與重新排序依據。

推薦時應優先選擇用途相同的頁面。例如，查看「關於我們」頁面時，先推薦其他網站的「關於我們」設計，而不是外觀接近的商品頁。每項推薦應顯示主要相似原因，例如「相同頁面類型」、「相近配色」或「相似卡片版面」，讓使用者理解推薦依據。

相似設計預設只使用各頁面的最新公開版本，並排除目前頁面、重複項目與無法正常顯示的資料。同一類型的資料不足時，可以逐步放寬其他條件，但不能悄悄混入用途不同的頁面；介面要清楚標示放寬了哪些條件。

### 先建立可靠資料，再增加功能

第一版的優先順序是擷取可靠、分類可用、搜尋找得到。任何不能提升這三件事的功能，都不應搶在核心流程穩定前開發。

自動裁切選單與內容清單很有價值，但它們依賴可靠的頁面擷取與 DOM（文件物件模型）分析。跨網站比較、Figma 整合與面向第三方開放的 API 則建立在穩定的資料結構之上。開發順序應遵守這些依賴，而不是同時做出多個不完整入口。

### 公共分類與個人整理分開

產業、網站語言、頁面類型、風格、動畫等級與頁面結構是平台用來檢索的公共資料，應由受控的分類規則管理。網站語言要分成主要語言與其他支援語言，多語系網站不能被迫只歸入單一語言。語言資料以實際擷取內容為依據，並保留人工修正能力，避免只根據網域或瀏覽器設定推測。

每個頁面都要有一個主要頁面類型，必要時可以加上次要標籤。頁面類型包含首頁、關於我們、產品或服務、案例、價格、最新消息列表、最新消息內容、部落格列表、部落格內容、常見問題、人才招募與聯絡我們等。分類要根據頁面內容、導覽文字與結構判斷，不能只看網址路徑，並且要允許人工修正。最新消息列表與單篇最新消息的設計用途不同，必須分成不同類型。

會員建立的收藏標籤是個人資料，名稱與組織方式由會員決定。會員可以自行建立、重新命名與刪除標籤，並替同一個收藏加上多個標籤。

收藏的基本單位是頁面，不是圖片或整個網站。圖片與框選視角是該頁面版本的視覺預覽，收藏紀錄則引用頁面及會員收藏當下看到的頁面版本。會員可以替每個收藏頁面新增、修改或刪除一段收藏原因，並直接在收藏圖片下方閱讀。頁面日後產生新版本時，原收藏仍顯示收藏當下的視角與原因，另外提供前往最新版本的入口，避免新版畫面與舊收藏原因互相矛盾。

公共分類與私人標籤不能共用同一套資料，否則會員命名會污染公共搜尋結果，公共分類調整也可能破壞會員原有的整理方式。會員收藏應引用頁面與頁面版本，不複製擷取內容；收藏原因屬於建立它的會員，不進入公共搜尋或公共標籤。

### 自動化必須容許失敗與重試

網站可能有登入限制、反爬蟲機制、地區差異、載入失敗或無限滾動。擷取失敗不能產生一筆看似有效的空資料，也不能因為工作重試而重複建立網站。

每個收錄 API 請求與後續分析都應有明確狀態，並能安全重試。同一個請求重送時不能重複建立網站、頁面或工作。只有完成必要檢查的結果才能公開；失敗與待確認的結果保留在內部流程，供重新處理或人工檢查。外部網站的 robots 規則、使用條款與內容權利也必須納入正式上線前的檢查。

### 原始證據與分析結果分開保存

頁面截圖、擷取時間、最終網址與必要的頁面結構是分析的原始證據；產業、語言、頁面類型、風格、色彩與分數是根據證據產生的結果。兩者應分開保存並保有關聯。

這項區分讓平台能在模型或分類規則更新後重新分析既有資料，不必重新拜訪每一個網站，也能追查某個標籤或分數是根據哪一次擷取產生。

### 桌面擷取使用固定基準

第一版的桌面畫面一律使用 `1920 × 1080` viewport（視窗尺寸）與 `device scale factor = 1`。同一次擷取要保存首屏與完整頁面：首屏用來比較使用者打開網站時立即看到的構圖，完整頁面用於瀏覽、框選、頁面類型判斷與相似設計搜尋。完整頁面維持 `1920` 像素寬度，高度依實際頁面內容決定。

擷取工作應等待網路與字型進入穩定狀態，停用動畫並固定瀏覽器版本、語系與時區；cookie banner（Cookie 提示）、輪播、時間及廣告等易變內容要保存辨識資訊，供版本比較降低權重。若日後加入手機或其他桌面寬度，必須建立新的擷取設定與版本識別，不能覆蓋 `desktop-1920` 的既有圖片。這能讓同一頁面的歷史畫面在相同條件下比較，避免瀏覽器環境差異被誤判成網站改版。

### 每筆資料都有可追溯的建立時間

所有寫入正式資料庫的資料都必須記錄 `created_at`，包括網站、頁面、頁面版本、圖片紀錄、公共標籤、AI 分析結果、收錄工作、會員、收藏、收藏視角、收藏原因、私人標籤、標籤關聯與使用行為。建立時間由伺服器在資料建立時產生，建立後不可改寫，也不能相信呼叫端自行提供的時間。

建立時間只表示這筆資料何時進入系統，不能拿來代替其他時間。頁面版本另有擷取時間，AI 結果另有分析時間，外部內容可另有發布時間，可修改資料另有最後更新時間。這些時間各自保存，避免網站早已發布，但因為剛被收錄就被誤認為新內容。

時間在資料庫中統一使用 UTC 保存，介面顯示時再轉換成使用者所在地區的時間。搜尋索引可以複製建立時間供排序與篩選，但 PostgreSQL 內的值才是正式依據。

## 初期部署與資料架構

### 本機是第一個正式運行環境

初期系統只運行在開發電腦，不接受其他電腦連線。這個階段不建立公開網域、區域網路入口、公開註冊入口或外部可存取的管理介面。

初期所有發布到開發電腦的應用程式連接埠只綁定 loopback interface（回送介面），例如 `127.0.0.1` 或 `localhost`，不提供區域網路或公開網路連線。容器之間只透過 Docker 內部網路溝通，不把資料庫連接埠對外發布。需要讓其他電腦使用時，視為新的部署階段，必須重新設計身分驗證、TLS（傳輸層安全性）、防火牆、秘密管理與存取紀錄，不能直接把本機連接埠對外開放。

這個階段先不以硬體規格作為開發前置條件，也不預先承諾可處理的網站數量或速度。實作時記錄單頁擷取時間、圖片容量、AI 分析時間、佇列等待時間與失敗率，再以開發電腦上的實測結果決定是否需要調整資源或拆分服務。

不公開服務不代表完全離線。擷取器仍須連外讀取目標網站；初期 AI 分析由 Codex 執行時，交給 Codex 的頁面圖片、頁面文字與必要中繼資料可能離開開發電腦。正式放入真實或敏感資料前，必須依實際使用的 Codex 方案與帳號設定確認資料處理方式；若未來要求資料不得離開內部環境，才改評估可在本機執行的模型。

本機硬碟是單一故障點。資料庫與圖片至少要定期備份到另一個儲存裝置，並實際驗證能從備份還原。備份不能只放在同一顆硬碟的不同目錄。

### 正式資料與搜尋索引分開

初期技術組合採用收錄 API、PostgreSQL、pgvector、本機檔案儲存、Playwright worker（背景工作程式）與 Docker Compose，各自負責不同資料：

| 元件 | 職責 |
| --- | --- |
| PostgreSQL | 保存網站、頁面、頁面版本、公共標籤、會員、收藏、框選範圍、收藏原因、私人標籤、擷取紀錄與使用行為，是唯一正式資料來源 |
| pgvector | 在 PostgreSQL 內保存並搜尋圖片與文字的 embedding（向量表示），支援第一版的相似設計與語意搜尋 |
| 本機檔案儲存 | 透過可替換的 `ObjectStorage` 介面保存預覽圖、完整頁面圖片、系統裁切圖、收藏視角的快取預覽與歷史版本；資料庫只保存檔案識別資訊及關聯 |
| 收錄 API | 只在開發電腦的 `localhost` 接受網址與工作操作，建立可追蹤且可安全重試的收錄工作，不對前台、區域網路或公開網路開放 |
| Playwright worker | 接收收錄工作後擷取網站並建立圖片與必要的頁面資料，不直接決定資料是否公開 |
| Codex 工作介面 | 提供本機 CLI（命令列介面），讓 Codex 取得待分析工作、讀取必要證據並提交結構化分析結果；所有寫入仍須經過收錄 API 驗證 |
| Docker Compose | 在內部電腦啟動並管理上述服務，讓開發與運行環境可重建 |

背景工作初期以 PostgreSQL 保存佇列狀態，不先加入 Redis、Kafka、Spark、Hadoop 或圖形資料庫。只有實際發生工作延遲、分析負載影響主要查詢，或行為資料需要獨立訓練時，才拆出相應服務。

收錄 API 即使只在 `localhost` 運行，仍必須驗證呼叫端、網址格式與工作識別資訊，並拒絕會連向內部網路或主機管理端點的網址。API 接受請求後先回傳工作識別資訊，由背景工作完成擷取，再等待 Codex 分析；呼叫端透過工作狀態得知處理中、完成、失敗或待人工確認。Codex 或擷取工作暫時失敗時，重試同一個工作，不建立平行資料。

### 初期 AI 由 Codex 協助處理

第一版把 Codex 定位為在開發電腦上執行的 AI 分析者，由開發人員啟動 Codex 任務後批次處理佇列，不把單次對話工作階段當成永久在線的背景服務。系統提供一組可重複使用的本機 CLI，讓 Codex 依序領取待分析工作、取得該版本的截圖與必要頁面資料、回傳符合 schema（資料結構規格）的 JSON，最後由收錄 API 驗證並寫入資料庫。OpenAI 的 Codex 使用案例也建議用可組合的 CLI，讓 Codex 安全讀寫 API 或本機資料來源。[OpenAI Codex 使用案例](https://developers.openai.com/codex/use-cases)

Codex 不直接連線或修改 PostgreSQL，也不能自行跳過品質檢查發布資料。分析輸出至少包含頁面主要與次要類型、主要與支援語言、產業、風格、色彩、版面特徵、動畫等級、美感分項、判斷依據與建議標籤。伺服器必須檢查欄位、允許值、信心程度與所屬頁面版本；不符合契約的結果留在待處理狀態，不得以缺省值假裝完成。

每次 Codex 執行都要記錄工作識別資訊、使用的模型或 Codex 環境、提示與分類規則版本、輸出 schema 版本、開始與完成時間、結果狀態及人工修正。這些紀錄讓相同證據可以重新分析，也能在分類規則改變後比較結果。初期允許人工觸發與覆核；自動常駐輪詢、無人值守執行與大量平行分析不屬於第一版，確定需要時再改成可程式化的模型 API 工作流程。

pgvector 支援精確與近似向量搜尋、HNSW 與 IVFFlat 索引、條件過濾，以及與 PostgreSQL 全文搜尋組合，足以驗證第一版的圖片、語意與條件混合搜尋。[pgvector 官方文件](https://github.com/pgvector/pgvector)

### 搜尋介面從第一版就保持可替換

搜尋功能不能直接散落在頁面 API 或資料庫查詢中。系統應定義獨立的搜尋介面與固定的搜尋文件格式，內容包含頁面類型、語言、產業、公共標籤、圖片與文字 embedding、色彩、版面、風格、品質分數及公開狀態。

圖片索引除了完整頁面，也要包含系統辨識出的頁面區域，例如首屏、導覽選單、卡片清單與內容區塊。使用者框選任意區域時，系統為該區域產生查詢 embedding，優先比對其他頁面的區域索引，再以整頁特徵重新排序。保存收藏視角時，該 embedding 應記錄模型版本，讓相同視角日後可以重新分析。

第一版由 PostgreSQL 與 pgvector 實作這個介面。公開部署或資料量增加後，可以加入 OpenSearch 作為搜尋索引，提供關鍵字、語意、圖片與條件混合搜尋；PostgreSQL 仍是正式資料來源，OpenSearch 索引必須能由 PostgreSQL、本機檔案儲存與模型版本資訊完整重建。OpenSearch 官方支援詞彙、語意、多模態與混合搜尋，適合作為後續搜尋層。[OpenSearch 搜尋概念](https://docs.opensearch.org/latest/vector-search/getting-started/concepts/)

Pinterest 式搜尋採兩階段。第一階段快速找出符合頁面類型、語言、產業、關鍵字與向量相似度的候選頁面；第二階段再依用途、視覺、品質、更新狀態與使用者偏好重新排序，最後排除重複內容並維持結果多樣性。初期沒有足夠行為資料時以內容特徵排序；搜尋、點擊、收藏、私人標籤與前往原站等事件累積後，再加入個人化排序。Pinterest 公開的推薦架構同樣採候選生成後再精確排序的多階段方式。[Pinterest Engineering](https://medium.com/pinterest-engineering/establishing-a-large-scale-learned-retrieval-system-at-pinterest-eb0eaf7b92c5)

每次 embedding 都要記錄模型名稱、模型版本、產生時間與所屬頁面版本。更換模型時建立新的結果，不覆蓋舊資料；確認新模型可用後再切換搜尋索引。這樣才能重新分析、比較結果，也能在模型或搜尋引擎更換時保留回退路徑。

## 第一版範圍

第一版要完成兩條可驗證且互相隔離的流程。收錄流程由內部系統透過受保護的 API 傳入網址，系統檢查是否已收錄、找出同一網站可公開存取的內頁、擷取頁面畫面、標註頁面類型、分析設計特徵，經過品質門檻後公開。前台流程只讓使用者搜尋已公開資料、查看頁面、框選相似設計、收藏頁面並建立自己的標籤版圖。

收錄 API 是第一版的阻擋性前置功能。沒有完成「API 接收網址、建立工作、擷取與截圖、交給 AI 分析、保存並發布」這條端到端流程，系統就沒有可供搜尋的內容，不能把第一版視為可用。

第一版包含：

- 只綁定開發電腦 `localhost` 的收錄 API，包括呼叫端驗證、網址驗證、重複請求保護、工作狀態與失敗重試。
- 供 Codex 使用的本機 CLI，包括領取待分析工作、讀取該頁面版本的證據、提交符合 schema 的結果，以及由收錄 API 驗證後保存；初期由開發人員啟動 Codex 任務，不要求常駐無人執行。
- 所有正式資料與關聯都記錄不可變的建立時間；具備不同意義的擷取、分析、發布與更新時間使用獨立欄位。
- 網址正規化、重新導向解析與重複網址檢查。
- 在受控範圍內找出同一網站的內部連結，避免爬取無限分頁、搜尋結果或重複內容。
- 全頁畫面擷取，以及失敗、重試與待檢查狀態。
- 相同網址的畫面差異檢測與頁面版本保存。
- 基礎產業、網站主要語言與支援語言、頁面類型、風格、色彩、動畫等級與美感評分。
- 網站與頁面圖庫、頁面類型篩選、基本篩選及詳情頁；每個頁面項目都要顯示對應圖片與原始頁面連結。
- 頁面詳情的相似設計推薦，以及推薦項目的主要相似原因。
- 頁面圖片的框選、移動、縮放與清除操作；框選區域能即時驅動相似設計搜尋，也能連同頁面版本保存為收藏視角。
- 本機階段的單一管理者或本機帳號登入；身分驗證與會員資料之間保留獨立邊界，以便公開部署前接上第三方登入。
- 頁面收藏、收藏視角、私人標籤與收藏原因，包括同一頁面保存多個不同視角、標籤的建立與管理、替單一收藏套用多個標籤，以及在收藏圖片下方新增、修改或刪除收藏原因。

導覽選單與內容清單的自動辨識可以在核心擷取流程穩定後加入第一版，或作為緊接著的功能階段。是否納入第一版，應以真實網站上的辨識成功率決定，不能只用少量示範網站判斷完成。

## 第一版不做的事

第一版不處理收費。系統不需要訂閱方案、付款、用量計費、付費刊登或免費版與專業版的權限差異。資料結構也不應為尚未確認的價格方案預先加入複雜的計費規則。

以下功能保留為後續可能方向，但不屬於第一版承諾：

- 把 Codex 或其他模型改造成常駐、無人值守且大量平行執行的 AI 背景服務。
- 跨網站並排比較選單或內容清單。
- Figma Plugin（Figma 外掛）與設計樣式同步。
- 供使用者投稿網址的 API 與提供第三方開發者使用的公開 API；內部收錄 API 不在此列，且是第一版必要功能。
- 公開網域、公開註冊與第三方登入；這些功能在正式公開部署前加入。
- 使用者輸入網址、社群投稿、公開個人收藏或協作分類。
- 商業訂閱與精選刊登。

## 成功標準

第一版是否成功，不以網站收錄總數判斷。更重要的是資料是否可信，以及使用者能否找到適合的案例。

核心衡量方向包括：

- 每筆正式資料都能查到由伺服器產生的建立時間，且不會與擷取、分析、發布或更新時間混用。
- 內部系統能透過收錄 API 與 Codex 工作介面，完成從網址、截圖、結構化 AI 分析到公開且可搜尋資料的完整流程。
- Codex 能領取指定工作、讀取對應頁面版本的證據並提交符合 schema 的結果；無效結果不會寫成已完成或公開資料。
- 前台沒有輸入網址或觸發網站擷取的入口，會員操作不能建立收錄工作。
- 收錄 API 只能從開發電腦本機連線，區域網路與公開網路無法存取；相同工作重送不會產生重複網站、頁面或背景工作。
- 同一頁面不會因網址格式或工作重試而產生無關聯的重複項目。
- 頁面重大改版能建立新版本，日常內容變化不會造成版本氾濫。
- 每個公開內頁都有可用的主要頁面類型，列表頁與內容頁不會混為同一類。
- 每個公開頁面的圖片都能追溯到相同版本的網址與擷取時間，並可從搜尋結果或詳情直接前往仍有效的原始頁面。
- 使用者能用產業、網站語言、頁面類型與主要視覺特徵縮小搜尋範圍。
- 頁面詳情能帶出用途與視覺特徵相近的其他設計，推薦結果不包含目前頁面或重複項目，並能說明主要相似原因。
- 使用者能在完整頁面圖片上拖曳、移動及縮放選取框；相似結果會隨選取區域更新，收藏清單也會準確顯示保存的視角。
- AI 分析結果能說明依據，並可追溯到擷取資料與分析版本。
- 內部使用者能登入本機版本，收藏頁面、建立私人標籤、替收藏套用多個標籤，並在收藏圖片下方維護自己的收藏原因；其他帳號不能查看或改動這些私人資料。
- 本機服務不會意外暴露到公開網路，資料庫與圖片備份已通過還原驗證。
- 擷取或分析失敗時，系統不會公開不完整資料，且可以安全重試。

這些指標的數值門檻要在取得真實網站樣本後制定。理念階段先確立衡量對象，避免用沒有資料支持的數字製造不必要的承諾。

## 長期方向

當資料品質與核心搜尋穩定後，SiteSensory 可以逐步成為網站設計的版本資料庫。使用者除了尋找靈感，也能觀察同一品牌如何調整導覽、內容組織、色彩與互動方式，並比較不同產業在相同介面問題上的做法。

準備公開部署時，系統加入第三方登入、正式工作佇列與 OpenSearch 搜尋索引；行為資料足以支援個人化訓練後，再增加事件串流、分析資料庫或圖形推薦。這些服務延後導入，但資料關係、搜尋文件與事件格式必須從第一版保持可延伸，避免公開時重做核心資料。

後續功能應繼續服從同一項判準：它是否讓設計案例更容易被理解、找到與比較。若功能只增加操作數量，卻沒有改善資料品質或使用者決策，就不應優先開發。
